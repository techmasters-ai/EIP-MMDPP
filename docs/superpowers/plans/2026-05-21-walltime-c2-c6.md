# Wall-time Reduction Plan — C1.5 + C2 through C6

> **For agentic workers:** REQUIRED: Use `superpowers-extended-cc:subagent-driven-development` (if subagents available) or `superpowers-extended-cc:executing-plans` to execute this plan. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Cut graph-extraction wall time of the air_defense_v3 pipeline against the bdde417 baseline by ≥50% across two test documents (SA-2 11MB / Dvina 2.3MB) without regressing any of the 10 quality gates from [[extraction-baseline-bdde417]] or the 33-test SA-2+Dvina acceptance harness.

## C1.5 — Dispatcher robustness fix (pre-C2 hardening)

**Goal:** When `derive_ontology_graph` raises BEFORE any per-pass task is queued (e.g. `UnknownBundleError`, `ConnectionError` resolving manifest), the dispatcher must terminalize cleanly: stage_run FAILED + pipeline_run FAILED. When the exception happens AFTER one-or-more per-pass tasks have already been queued, behavior is different — see semantic decision below.

**Why:** Discovered 2026-05-21 — a stale worker-1 couldn't see the new subset bundle, the dispatcher raised `UnknownBundleError`, but the stage_run was marked RUNNING *before* the bundle resolve. The exception bubbled through the celery guard but no FAILED transition was emitted, leaving the pipeline_run wedged in PROCESSING for 8 hours. Future regression tests will hit this any time the dispatcher partially fails.

**Semantic decision (forced by review):** `is_run_cancelled()` (`app/services/run_phase_dispatch.py:438`) treats `status='FAILED'` as cancelled. Any already-queued pass task that calls `is_run_cancelled()` will bail. The plan must pick ONE of these behaviors:

  - **Option Pre-Only (Recommended):** Terminalize PipelineRun=FAILED ONLY when the exception happens BEFORE the first per-pass task was queued. Once at least one task has been queued, the dispatcher stage_run is still marked FAILED, but the pipeline_run is LEFT in PROCESSING so the queued passes run to completion. The reconciler then handles the terminal transition based on what those passes produced.
  - **Option Fail-Fast:** Always terminalize PipelineRun=FAILED on dispatcher failure, even if some passes were queued — accepting that those queued tasks will bail at their next cancel-check. Simpler but loses partial-work value.

Recommend Option Pre-Only — preserves any successful upstream work and gives the reconciler a clean view.

**Files:**
- Modify: `app/workers/pipeline.py` (~line 7772, `derive_ontology_graph` task body)
- Test: `tests/unit/test_derive_ontology_graph_dispatcher_failure.py` (new)

**Acceptance:**
- `derive_ontology_graph` task wraps its per-pass dispatch logic in try/except.
- On pre-queue exception (no passes queued yet): dispatcher stage_run FAILED + pipeline_run FAILED + error_message set.
- On post-queue exception (≥1 pass queued before the failure): dispatcher stage_run FAILED, pipeline_run stays PROCESSING, reconciler handles eventual terminal state.
- A new unit test for the pre-queue path: mock the bundle loader to raise `UnknownBundleError`, invoke `derive_ontology_graph` directly, assert (a) stage_run row written with FAILED, (b) PipelineRun status moved to FAILED, (c) no Celery `.delay()` calls were made.
- A second unit test for the post-queue path: mock to allow N pass dispatches then raise on (N+1), assert PipelineRun stays PROCESSING + stage_run FAILED with error_message naming the queued count.

**Open scope decisions (Task 1 — discussion gate):**
- (a) Pre-Only vs Fail-Fast (above). Recommend Pre-Only.
- (b) Are there OTHER stages with the same RUNNING-without-cleanup bug (e.g. `derive_text_chunks_and_embeddings`)? Recommend: scope just `derive_ontology_graph` for this fix and TODO the broader audit.
- (c) Should the fix include an UPSERT path so a re-run can reclaim a stuck-RUNNING row? Recommend: leave reclaim to the `reconcile_ontology_graph_runs` heartbeat; fix prevents *new* stuck states.

## C1.6 — First-class pass phase model (prerequisite for C3 + C4)

**Goal:** Replace the implicit "any pass with empty `depends_on` is an entity pass" rule (`pipeline.py:6995`) with an explicit `phase: identity | field_group | relationship` declared per manifest pass. `_try_advance_phase` Branches 1/2/3 then operate on phases, not on the emptiness of `depends_on`. This is the load-bearing prerequisite for C4b (identity-first ordering) and C3 (router fired at the right dispatch chokepoint).

**Why:** Discovered in review of rev 2 — if C4b adds `depends_on: [radar_identity, missile_identity]` to field-group passes to enforce ordering, those field-group passes drop OUT of the implicit "entity_passes" set (`[p.name for p in manifest.passes if not p.depends_on]` at line 6995). Branch 2 of `_try_advance_phase` would then dispatch `system_links` as soon as the identity passes resolve — BEFORE field-group passes complete. The whole identity-first design collapses without explicit phases.

**Files:**
- Modify: `app/services/ontology_bundles.py` (`BundleManifest`/pass def — add required `phase: Literal["identity","field_group","relationship"]` field; default = derived from current logic for back-compat read, but new bundles must declare it).
- Modify: `ontology_bundles/air_defense_v3/manifest.yaml` + `ontology_bundles/air_defense_v3_baseline_subset/manifest.yaml` — annotate every pass with `phase:`. Identity = `radar_identity`, `missile_identity`. Field-group = the other 9 entity passes (or 2 in the subset). Relationship = `system_links`.
- Modify: `app/workers/pipeline.py:_try_advance_phase` — Branches rewritten in phase order:
  - **Branch 1** (identity): dispatch next identity pass while in-flight < cap.
  - **Branch 2** (field_group): only AFTER all identity passes terminalize. Dispatch field-group passes while in-flight < cap.
  - **Branch 3** (relationship/system_links): only AFTER all field_group passes terminalize (or after identity if no field_group passes exist in the bundle).
  - **Branch 4** (merge): only AFTER relationship pass terminalizes.
- Modify: `_claim_and_dispatch_pass` (called by Branch 1/2/3) — single chokepoint where C3's router check will land later.
- Test: `tests/unit/test_pass_phase_model.py` — manifest validation: every pass has a phase; phases sort in order identity → field_group → relationship.

## C4 — Identity-first chunk narrowing (Phase 4) ★largest expected gain★

**Goal:** Run identity passes first (`radar_identity` + `missile_identity`), build an entity alias roster, then send only top-K relevant chunks to each field-group pass — not the whole document. Whole-doc fallback only when no candidates found AND the pass is important.

**Why:** From the user's original plan: "Large SA-2 style docs should drop field-group batch counts from ~50-60 to a much smaller number." Architecturally the biggest payoff in the entire wall-time plan. Reuses C3's cue-list infrastructure.

**Top-level acceptance for the combined C4:**
- Field-group passes (`radar_power_rf`, `missile_kinematics`) on SA-2 produce ≤ 50% of baseline `batch_count` when chunk_scope narrows the doc.
- Identity recall on SA-2 stable (23 + 44 entities = matches gates #3 + #7).
- Field fill counts on SA-2 stable (gate #5 21/34 emitter_function; gate #6 9/44 min_altitude_km).
- Dvina extraction unchanged.
- field_provenance evidence_id round-trips through scope back to original self_refs.
- Acceptance harness 33/0 + all 10 quality gates hold.

**Top-level open scope decisions (must be resolved before C4a starts):**
- Top-K — `K = min(manifest.top_k or 20, all_matching_chunks)`.
- No-match fallback — RUN_FULL when `fallback_to_full: true` in manifest; SKIP via C3 mechanism otherwise.
- Embeddings deferred (lexical-only here).
- Roster persisted, NOT in-memory (per review finding 1 — see constraint below).
- Serial identity → field-group → system_links is the new ordering. Loses some parallelism; field-group passes get so much smaller that net parallelism becomes irrelevant.

**Critical architectural constraint (forced by review finding 1):** `derive_ontology_graph` is a **dispatcher only** — it queues per-pass Celery tasks and returns. Per-pass workers run separately, so the alias roster CANNOT be an in-memory dict passed via worker state. The roster must be PERSISTED, and the dispatcher's phase advancement state machine (`_try_advance_phase`) must wait for identity passes to complete BEFORE field-group passes are queued.

**Critical service-side constraint (forced by review finding 4):** Docling refs are index-based (`#/texts/N`, `#/tables/N`). Dropping array items breaks every higher-index ref. The C0-era `_sanitize_docling_document` preserves array positions by BLANKING text (`text=""`, `orig=""`) — not removing items. The scoped DoclingDocument builder MUST follow this pattern: preserve original `texts[]` / `tables[]` arrays + only rewrite `body.children` to traverse a narrowed subset.

## C5 — Cache prepared inputs (Phase 5)

**Goal:** docling-graph caches prepared artifacts across the multiple `/extract-pass` calls a single pipeline_run makes. Split into two cache LAYERS because preparation is partly pass-agnostic and partly pass-specific (per review finding 5).

**Why:** From the user's plan: "Repeated per-pass prep time drops near zero after first pass." With C0 telemetry, we can directly measure `sanitize_ms + table_normalization_ms + table_overlay_ms` per pass — that sum is the win.

**Two-layer cache shape (review finding 5):**

- **Layer A — Global (pass-agnostic, scope-independent).** Key: `(document_id, content_hash)`. Caches the FULL sanitized base doc:
  - sanitized DoclingDocument JSON (input to ALL passes, ANY scope) — pre-scope, full arrays
  - table-overlay parser result (independent of pass + scope; same overlay for every pass on the same doc)
  - per-doc evidence text buffer used by service identity filter

  **Ordering with C4 chunk_scope** (review finding 6): chunk_scope from C4d is applied AFTER the Layer A cache hit. Layer A's key intentionally does NOT include `chunk_scope_hash` — that would leak scope into a key that's supposed to be scope-independent. The flow on every `/extract-pass` is: Layer A lookup → (cache miss → sanitize + overlay + populate) → apply chunk_scope to the cached doc → continue to Layer B.

- **Layer B — Pass-specific.** Key: `(document_id, content_hash, pass_name, chunk_scope_hash, normalization_config_hash)`. Caches:
  - normalized table chunks (depends on `pass_name` because `_norm_skipped_for_pass` and table-relevance differ)
  - rendered TextItems from per-pass normalization (depends on `unit_convention`, `emit_unit_hint`)
  - chunk metadata + per-pass evidence units

These are SEPARATE caches in `_doc_cache.py`; misses on Layer B don't invalidate Layer A.

**Files:**
- Create: `docker/docling-graph/app/_doc_cache.py` — two cache classes, `GlobalDocCache` + `PassPrepCache`, both LRU + TTL.
- Modify: `docker/docling-graph/app/main.py:run_extraction_pass` — check global cache before sanitize + overlay; check pass-specific cache before normalize/render.
- Test: `docker/docling-graph/tests/test_doc_cache.py` — both cache classes; hit/miss; LRU; TTL; key-collision handling.
- Test: `docker/docling-graph/tests/test_extract_pass_reuses_cache.py` — pass 1 builds both caches; passes 2–5 on the same doc hit Layer A; passes 2–5 with the SAME `pass_name` hit Layer B; pass 1 of a different `pass_name` misses Layer B but still hits Layer A.

**Acceptance (review finding 5 — split per-layer):**

**Layer A (cross-pass, scope-independent) — applies whenever ≥2 passes touch the same `(document_id, content_hash)`:**
- Passes 2-N: `sanitize_ms < 5ms` AND `table_overlay_ms < 5ms`. (Layer A hit; `table_normalization_ms` is NOT in this target because Layer B owns it and DIFFERENT pass_names will miss Layer B by design.)

**Layer B (same-pass retries with the same scope) — applies when a pass retries on the SAME `(document_id, content_hash, pass_name, chunk_scope_hash, normalization_config_hash)`:**
- Retries 2-N of the SAME pass: ALL of `sanitize_ms < 5ms`, `table_overlay_ms < 5ms`, `table_normalization_ms < 5ms`.

**Both layers:**
- Cache evicts on TTL (default 1h) AND on content-hash mismatch.
- Memory ceilings: `DOCLING_GRAPH_DOC_CACHE_MAX_ENTRIES_A` + `DOCLING_GRAPH_DOC_CACHE_MAX_ENTRIES_B` (default 16 each; separate names to make per-layer tuning explicit).
- Acceptance harness 33/0 + 10 quality gates hold.
- Cache correctness verified by acceptance harness (same fixtures must produce same output post-cache; a stale Layer B entry returning wrong content for a new scope would corrupt extraction — caught by the 33 tests).

**Open scope decisions (Task 1 — discussion gate):**
- (a) Near-term in-process cache (per the user's plan) vs the better "send only document_id, service loads from MinIO" version? Recommend: near-term in-process this checkpoint; MinIO-side artifact key deferred.
- (b) Cache eviction policy — TTL only / LRU only / both? Recommend: both. LRU primary, TTL backstop.
- (c) `chunk_scope_hash` computation — hash of (sorted_self_refs + mode). Stable across runs.
- (d) `normalization_config_hash` computation — hash of (pass_name + token_limits + unit_convention + emit_unit_hint). Stable across runs.
- (e) On content-hash collision between two different runs: treat as cache hit (caller can't tell; content is byte-identical by construction).

## C6 — Merge / import cleanup (Phase 7)

**Goal:** After LLM time is reduced by C2–C5, the worker-side fan-in (especially `system_links` rehydration) becomes measurable. Persist compact upstream entity catalogs so `system_links` doesn't re-parse every upstream `extract_pass_response_json`; `lru_cache` worker-side manifest loads; prefer provenance-derived chunk links over O(entities × chunks) substring scans.

**Why:** From the user's plan: "Merge/import time is measurable and no longer dominated by reparsing large JSON blobs."
